# Pipeviewer

A small, dependency-free web app that maps stdin (0), stdout (1), and stderr (2) through a Unix pipeline. Type or paste a command and follow the coloured connections. The diagram updates as you type. Nothing you paste is sent to a server.

## Run

Requires Node.js 18 or newer.

```sh
npm start
```

Open http://localhost:5173. Use `npm run dev -- --port 3000` for a different port.

```sh
npm test       # Parser behaviour and redirect ordering
npm run build # Static files in dist/
```

Serve `dist/` with any static host, at a domain's root or under a subpath such as `/pipeviewer/`: every path in the page is relative. Under a subpath, link to it with the trailing slash, which nginx adds itself when the folder is reached through `try_files $uri $uri/`. No build dependencies or backend are needed. The build lists every module in `dist/index.html` as a `modulepreload`, so the browser fetches the command rules at once instead of one import level at a time. The interface uses optional Google Fonts with local fallbacks; the font stylesheet loads without blocking the first paint.

`./deploy-jellyfin.sh` tests, builds, and deploys to `https://pipeviewer.offelbrook.com` on the host `jellyfin`: it copies `dist/` to `/var/www/pipeviewer` over SSH, writes `/etc/nginx/sites-available/pipeviewer` (HTTPS and HTTP/2 with the `*.offelbrook.com` certificate in `/etc/letsencrypt/live/offelbrook.com/`, gzip for the code and icons, and HTTP redirected to HTTPS), links it into `sites-enabled`, and reloads nginx once `nginx -t` passes. If `nginx -t` fails, the previous site file is put back. The deployed copy hides the **Tips & Tricks** button with `style="display: none;"`; the source and local builds keep it. sudo on the server may ask for your password. The host, domain, folder and certificate are set at the top of the script.

The **Tips & Tricks** button plays a recorded talk from `video/`, which is not in git. Put the `.webm` file there before building, and `npm run build` copies it to `dist/video/`. Your static host must support HTTP range requests so the player can seek. The dev server supports them.

## Features

- **Training** mode, from the green button in the header, has three courses. **Toolbox** is a short whodunit for people new to the shell: each level hands over a tool such as `grep`, `cut` or `uniq`, runs the student's command on pretend files, and is solved when it prints what the target prints. **The Unix Way** runs commands the same way to show why Unix works as it does: everything is a file, small tools, streaming, quiet success, settings in text files, and package managers. **Plumbing** teaches redirects by picture: each level shows the diagram of a command the student can't see, and they edit a starting command until their own diagram matches it. See [Training](#training).

- Light, dark and terminal themes. The terminal theme is phosphor green on black, all monospace. The page follows the system's light or dark theme until you pick one with the theme button, which shows the current theme, steps through the three, and remembers your choice. In the terminal theme the command editor is a black terminal too. The editor names the shell the header's shell switch picks, and a faint Tux or apple watermark behind the page shows which system is being mapped.
- Coloured stream diagram with zoom controls, middle-click drag to pan, per-command descriptor mappings, and SVG export. On wide windows the page uses the full width so long pipelines need less scrolling.
- Static stream-usage hints distinguish connections from actual command behaviour. Includes a `sleep 2 | echo "hello, world"` example and explanations of output timing.
- Clickable examples, each with its related spellings under **Variations**, and a quick reference. Each Quick reference entry opens, one at a time, to explain more, with at least one example; the play button on an example draws it in the viewer, outside training. The entries live in `reference.js`. Clicking the chosen example again clears the editor. In the Variations, Redirects and Examples rows, the chosen button sits on a thumb that slides from button to button. The **Redirects** switch shows any pipeline, an example or your own, in the common style (`< file`, `> file`, `>&2`), the default, or the explicit one (`0< file`, `1> file`, `1>&2`). Variations and Redirects show their buttons only when the pipeline has something for them.
- Lists of pipelines joined by `&&`, `||`, `;`, or new lines, stacked in the order they run, each labelled with when it runs.
- Left-to-right redirects, including descriptor snapshots and pipe overrides.
- `|`, `|&`, `<`, `>`, `>>`, `>|`, `n>&m`, `n<&m`, `&>`, `&>>`, and descriptor closing.
- Process substitution: `2> >(cmd)`, `< <(cmd)`, and `<(cmd)` or `>(cmd)` as arguments (passed as `/dev/fd/63`, `/dev/fd/62`, …). Substitutions can hold their own pipelines and redirects. One used as a redirect target inherits the owning command's descriptors at its position in the left-to-right redirect order; one used as an argument is expanded before any redirect, so it gets the pipeline's pipes but none of the command's redirects. For example, `cat` in `echo hi 2> >(cat) | xargs` writes to the same pipe as `echo`'s stdout.
- `xargs` running a shell script per item (`xargs -P 8 sh -c '… "$1" …' _`) is drawn the same way. Its jobs read `/dev/null` and write straight to `xargs`'s stdout and stderr, and the script follows Bash's rules even on macOS, since `sh` is not zsh.
- GNU `parallel` job commands that parse as pipelines are drawn as a stacked job template below `parallel`. It runs once per argument, with stdin from `/dev/null` (or blocks from `parallel` with `--pipe`), and `parallel` collects its stdout and stderr. With `-u`, jobs write straight to `parallel`'s stdout and stderr. Commands without a replacement string such as `{}` have the arguments appended, as `parallel` does.
- Redirects to `/dev/tty` reach the terminal: reads connect to terminal input, stderr to terminal stderr, and other writes to terminal output.
- `/dev/stdin`, `/dev/stdout`, and `/dev/stderr` redirect to the current destination of 0, 1, or 2, like a descriptor copy. When that destination is a file, the step notes that Bash opens it again with a separate offset.
- A stream to or from the terminal ends in a small **terminal** tag beside its port instead of a route to a shared box, much as circuit diagrams mark ground. The tag is coloured for the terminal stream it reaches, green for input, purple for output and amber for errors, so stdout sent to the terminal's stderr with `>&2` ends in an amber tag. A closed descriptor, as `2>&-` leaves stderr, ends in a grey **closed** tag.
- A file that only one stream uses ends in a small tag beside that port, naming the file. stderr's fits in the gap before the next card, and where a card sits beside stdin or stdout, their tag rises into the space above the pipe between the two, as `response.html` does in `curl https://example.com 2>&1 > response.html | grep "error"`. A file two streams share, as in `make 1> build.log 2>&1`, keeps its box so the drawing shows both reaching it. `/dev/null`, `/dev/zero`, `/dev/full` (Linux only), `/dev/random` and `/dev/urandom` get their own glyphs and a word on what a read or a write does, in tags and boxes alike. The **Tags** switch in the diagram toolbar brings back the routes for both. The key under the diagram lists only what the drawing holds, so it names only the terminal streams that end in a tag, and shows the closed and file samples only when there is one.
- Each routed stream gets its own lane; hover a line to fade the others and trace it.
- The **Highlight** button in the diagram toolbar turns the linking between the command and the diagram on or off, in both directions.
- The diagram follows the editor caret, like a browser's element inspector: a command lights its card and streams, a redirect its port and destination, and `|` its pipe. Commands inside process substitutions and `parallel` jobs light up too. It works the other way too: hover part of the diagram to mark its text in the editor, and click to select it.
- Descriptors above 2 that stay open are drawn on their card. One left writing to the pipe to the next command, as `3>&1 1>&2 2>&3` leaves fd 3, gets a port on the card's bottom edge and a line into that command's stdin, since it keeps the pipe open. The others are listed in the card's lower-left corner with where they point. One used and then closed, as with `3>&-`, is listed as closed.
- Quoted arguments and destinations, escapes, and additional descriptor bookkeeping.

## Training

The Training button opens on a picker with a card for each course, so everyone sees that there's more than one: **Toolbox** for people new to the shell, **The Unix Way** for why it all works as it does, and **Plumbing** for people who know their way around and want their redirects sharp. The last level of each leads on to the next in that order. Each card says who it's for, plays a small looping preview, and shows the student's stars and where they'd carry on. Once in, a switch at the top of the training screen moves between courses. Each course keeps its own levels, stars and tour. The cards are drawn from `tracks` in `app.js`, so a new course gets its card with its entry there.

### Toolbox

Someone has emptied the Tim Tams in the level 3 kitchen, and the student has the case file: a README, the smart pantry's lists from 15:00 and 15:10, a week of badge swipes, a staff list, and a note found in the bin. Twelve levels, numbered from 1, take about ten minutes and hand over one tool or idea each: `ls`, `cat`, `head`, `wc`, `diff`, `grep`, `|`, `cut`, `sort` and `uniq`, `sort -rn | head`, `grep -w`, and `tr` to decode the note, which is in ROT13. Levels 7 to 10 grow one pipeline a stage at a time, so the student watches a list of swipes narrow down to one name.

The student's command runs as they type, in a sandbox in the page (`sandbox.js`), and what it prints appears under the editor as a terminal would show it, with stderr in amber. Above it, the screen keeps a scrollback, as a terminal does: each earlier level the student has solved, with the command as they wrote it and what it printed, dimmed, so a clue found in one level is still on screen in the next. The screen stays scrolled to the bottom unless the student scrolls up, `clear` empties it, and the solved commands are kept in local storage, so the scrollback survives a reload. Beside it, the goal is the target's output blacked out word by word, so its shape shows: how many lines, how many words on each. Each line uncovers when the student's line in the same place matches it, and the level is solved when every line matches. Lines are compared by their words, so `uniq -c`'s GNU and BSD padding both pass, and any command that prints the same solves the level: `grep -w jlee staff.txt` and `grep ^jlee: staff.txt` alike. The diagram stays below, so the pipe being built is still drawn.

The sandbox runs the parsed command line, so redirects, pipes, `&&`, `||` and globs behave as the diagram says, on a copy of the case files. The shell empties a file it writes to before the pipeline runs, so `sort f > f` leaves `f` empty, as it would for real. It has `ls`, `cat`, `head`, `tail`, `wc`, `grep` (basic and extended patterns), `sort`, `uniq`, `cut`, `tr`, `diff` (normal and `-u`), `comm`, `sed` (`s`, `d`, `p` and `q`), a small `awk` that prints fields, `tee`, `echo`, `printf`, `rev`, `tac`, `nl`, `seq`, `yes`, `base64`, `cp`, `mv`, `rm`, `mkdir`, `touch`, `sysctl`, `tty`, `uname`, `hostname`, `sudo`, `apt` and `brew`, and `man`, whose pages are the same cards the hints show. `apt` and `brew` install `cowsay` and `fortune` from a pretend repository, for the rest of the command line. The system has `/dev/null`, `/dev/zero`, `/dev/urandom` and `/dev/tty`, an `/etc` with `passwd`, `hostname` and `ssh/sshd_config`, and on Linux a `/proc` with `cpuinfo`, `meminfo` and `uptime`. `/dev/zero` and `/dev/urandom` stop after 1.5 MiB, and the random bytes come from a fixed seed so an answer can be checked. Bytes a terminal can't show appear as �. Their output and errors follow GNU coreutils, or the BSD tools' spacing for `wc` and `uniq -c` in macOS mode. An unknown command gets Bash's or zsh's `command not found`. A command that would read the keyboard, such as `grep jlee` with no file, says so instead of hanging, and files a command writes are listed under its output. Process substitutions and `parallel` jobs aren't run.

The hints are **Which tool?**, which shows the cards for the level's tools, **Show me how** and **Answer**, each costing a star as in Plumbing. A row of chips under the brief is the toolbox: each tool is filled in once a level that uses it is solved, and the ones still to come are faint outlines. A solved level shows any new tool's card, and the last one offers Plumbing next.

### Toolbox, the standalone page

`toolbox.html` is a second take on Toolbox, built from a blank slate and kept apart from the training screen so the two can be compared. It shares only the sandbox, the parser and the case files.

The terminal is the whole exercise. Commands run on Enter, ↑ and ↓ walk the history, Tab completes a command or file name (listing the choices when there are several), Ctrl-C abandons the line, and `clear` or Ctrl-L clears the screen. `help` lists the tools and `history` the commands typed. There are no levels: a case notebook beside the terminal holds seven questions (what's in the case file, what happened, when, who went into the kitchen, who went in most, who jlee is, and what the note says), and each is ticked off when its answer reaches the screen, however the student got it there. The open question offers nudges one at a time, from a pointer to a command to try, which a click puts in the terminal. Once the student knows who went in most, Facilities send mail and `found-in-bin.txt` appears.

A pipeline's output carries an X-ray: a chip for each stage with how many lines it passed on, amber if it complained, and a click shows what that stage wrote. The first time a tool works, a chip says what it does, and it joins **Your tools**, whose cards open in the notebook. Under an error, a note explains the usual slips: a mistyped command (`grpe`, did you mean `grep`?), a file name with the wrong capitals, `tr` given a file name, or output too long to read. The session is saved as the commands typed, and replayed on the next visit; **Start over** clears it. On narrow screens the notebook folds to a line above the terminal.

### The Unix Way

Twelve levels, numbered from 1, each try out one idea on a pretend machine, with the same output, goal and hints as Toolbox. Everything is a file: `echo hello > /dev/tty` reaches the screen, `/dev/null` keeps nothing, `head -c 12 /dev/urandom | base64` makes a password, `grep -c processor /proc/cpuinfo` counts the processors, and `cut -d: -f1 /etc/passwd` lists the users. Do one thing well: Kernighan's spelling checker from the 1982 film, `tr | tr | sort -u | comm -23 - words.txt`, finds the four typos in a memo. Streams: a million random bytes go through `base64` while no command holds more than a pipe's buffer, and a level asks for the biggest of 100,000 numbers without `sort` holding them all. Then quiet success (`cp && diff && echo same`), settings as text files under `/etc` rather than a registry, and `sudo apt install cowsay` (`brew install cowsay` on macOS) from one central repository.

Under the output, each command gets a light for its exit status (green for 0, red otherwise, hollow if `&&` or `||` skipped it) and a gauge, on a log scale, for how much of its input it holds at once. The sandbox models this rather than measuring it: most tools stream, holding up to a 64 KiB pipe buffer, and `sort`, `tac`, `shuf` and `diff` hold everything they read. A level can set `memory`, the most any command may hold; its output must match and every command must stay under it.

Levels that work differently on a Mac say so in `mac`, which overrides any of a level's fields when the shell switch is on macOS: macOS has no `/proc`, so level 4 asks `sysctl -n hw.ncpu`, and Homebrew installs without `sudo`, refusing to run as root. The levels are in `unixway.js`, with the memo and word list they use.

### Plumbing

Levels are numbered from 0, as descriptors are. Level 0, **n00b**, is for complete beginners. It opens on short slides, each with one idea, an example command and a small animated picture: every program has stdin, stdout and stderr; they are numbered 0, 1 and 2; a pipe joins 1 on the left to 0 on the right; and McIlroy's 1964 garden-hose memo, with a three-command pipe. A last slide, *Rewind to 1982*, holds a drawn VHS tape of Bell Labs' 1982 film *The UNIX System*: clicking it plays *Making Computers Easier to Use* from YouTube (youtube-nocookie.com) at 5:14, where Brian Kernighan builds a spelling checker out of existing programs, using temporary files. Once played, the film fills the slide, over a strip of its chapters drawn to scale: Brian's temporary files, a section on files, and Lorinda Cherry's pipes, which are lit in purple. A playhead follows the film, from the time the player reports, and the pipes chapter pulses once it's reached. Nothing loads from YouTube until the tape is clicked, and leaving the slide stops it. **Your turn** then hands over to an ordinary level, where the student pipes `ls` into `head -n 3`. Arrow keys step through the slides, and **Skip to the exercise** jumps ahead. Training never opens on level 0: it starts at level 1, with the tour, so the student finds level 0 for themselves. Until they solve it, its button is tinted stdin's green, like the Training button. Each time they look stuck (they take a hint, restart a level, or leave a level unmatched for 40 seconds, not counting time in the tour) it pulses a few times, and it keeps a green outline until they solve a level without hints. The tour's picture step links to it.

Training opens with a crossfade. The first time a level's exercise is shown, a short tour dims the page and moves a spotlight from the training bar, to the command, to its picture, to the target, to the hints, with a card explaining each. **Show me around** runs it again.

Each level shows a target picture and a starting command, typed and drawn. The student edits the command until their picture matches the target's. On windows 64em wide or more the two pictures sit side by side under the editor: the student's on the left, just under where they type, and the target's on the right. Both are cropped to one shared frame so they are drawn at the same scale. On narrower windows the target sits above the editor. The training screen leaves out the viewer's key, insights, descriptor details and toolbar switches, and the caret doesn't fade parts of the picture, so nothing gets in the way of comparing the two. A ring marks each port whose stream goes somewhere else in the target, in both pictures, and a dashed outline marks a card whose words differ. The toolbar counts the differences.

Pictures are compared, not spellings. Two command lines match when they draw the same cards, with the same words after quote removal, and send every descriptor to the same place. So `sort <in >out`, `sort 0< in 1> out` and `>out sort <in` all solve the same level. Once a level is solved, the target's own command is shown above its picture, and the student's spelling is compared with it if the two differ.

A level is worth three stars. There are three hints: **What's different?** lists each difference in words, **Show me how** gives the syntax, and **Answer** shows the target command. Each is taken on its own, shows only itself, and costs a star, but a solved level always earns at least one. When the pictures match, the streams start to flow, and Enter or the button moves on to the next level, keeping the student's command as its starting point. Best stars per level are kept in the browser's local storage.

The shell switch in the header works in training too: the target is redrawn as the chosen shell runs it.

Link to `/#training` to open Plumbing at the first unsolved level, to `/#training/0` for the n00b slides, or to `/#training/2` for level 2. `/#toolbox`, `/#toolbox/3`, `/#unixway` and `/#unixway/3` do the same for Toolbox and The Unix Way, and `/#courses` opens the picker. The standalone Toolbox is at `/toolbox.html`.

### Adding a level

Levels are listed in `lessons.js`, in the order they're played. Each has an `id` (keep it fixed once published, since progress is saved under it), a `title`, a `brief`, a `target`, a `how` hint and a `learned` note shown once it's solved. `start` is the command in the editor when the level opens; leave it out to start from the previous level's target. Text in backticks is set as code. `label` replaces the level's number on its button, and `intro: true` shows the slides in `intro.js` before the exercise. Each slide there has a `title`, `text`, an `example` command with a `note`, an optional `quote`, and a `picture` that draws it. `npm test` checks that every target parses under both shells and that no level starts out already solved.

Toolbox levels are listed in `cases.js`, with the case files they run on. They have the same fields, minus `label` and `intro`, plus `tools`: the tools whose cards the first hint shows and which go into the toolbox once the level is solved. Each needs a card in `tools` in `sandbox.js`. `npm test` runs every target on both systems and checks that it prints something and no errors, and that no level starts out solved. The swipe log is made from a fixed seed, so the case comes out the same every time; the ten minutes that matter are written out by hand.

## macOS and zsh

The shell switch in the header, Tux for Linux and Bash and an apple for macOS and zsh, maps a command line as macOS runs it: under zsh, the default macOS shell, with the BSD and Apple versions of the tools. It starts on macOS on Apple devices and on Linux elsewhere, and remembers your choice once you pick one.

- zsh's MULTIOS option is on by default, so a redirect adds a destination instead of replacing the pipe or an earlier redirect. `cmd > out | grep x` sends output to both, and `cmd 2>&1 > /dev/null | grep x` gives grep both streams. The diagram draws a line to each target.
- Process substitutions are numbered from `/dev/fd/11`. One used as an argument gets the shell's own descriptors; one used as a redirect target sees the pipeline's pipes but not the command's redirects.
- A line of only redirects runs `cat`, or `more` for input. `#` does not start a comment at an interactive prompt, and only single digits name descriptors.
- Tools follow the macOS 15 builds: option strings come from Apple's sources (github.com/apple-oss-distributions), and the BSD tools stop reading options at the first file name. Many treat `-` as a file, `sed -i` takes a backup suffix, `base64` reads `-i FILE`, `date -f` is a parse format, and `zcat` wants `.Z` files (use `gzcat`). Commands macOS lacks, such as `tac`, `timeout` and `nproc`, show as unknown with the usual replacement. Mac tools such as `pbcopy`, `pbpaste`, `say`, `open`, `caffeinate`, `md5` and `sw_vers` are modelled.

The Wiki download and Wiki pageviews examples use GNU parallel, wget, pv and mawk, which stock macOS lacks, so in macOS mode they load versions built on `xargs -P`, `curl -Z`, `gzcat` and `dd status=progress`. Flipping the switch with one loaded swaps it for the other system's version.

The zsh rules were checked against zsh 5.8; macOS ships 5.9, whose changelog lists no changes to them.

## Adding a command

Each modelled command has a file in `commands/` that default-exports `{ names, infer(ctx) }`, plus optional `linux` and `macos` keys for where it ships. `ctx.platform` says which system is being mapped. `infer` reads the arguments in `ctx` and records what the command does with stdin, stdout, and stderr. `commands/index.js` describes `ctx` and lists every rule, and `commands/helpers.js` holds the shared option scanners and usage builders. To add a command, write its file, then import and list it in `commands/index.js`. The Quick reference picks the new name up from there, and `npm test` fails if a file in `commands/` is not listed.

## Scope

This is a static descriptor map of simple Bash-style pipelines, assuming the usual initial descriptors 0–2 are open. It recognises every GNU coreutils program, as installed by default on Ubuntu Server and most Linux distributions, from `[` to `yes`, plus `kill`, `uptime`, and `hostname`. It also recognises `awk` (with `mawk`, `gawk`, and `nawk`), `sed`, `grep` (with `egrep` and `fgrep`), `find`, `diff`, `xargs`, `parallel`, `zcat`, `rev`, `curl`, `wget`, `pv`, and `/usr/bin/time`, plus Homebrew's `brew`, `apt` and `apt-get` on Linux, and `softwareupdate` on macOS. Wrappers such as `sudo`, `env`, `nice`, `nohup`, `stdbuf`, `timeout`, and `chroot` follow the command they run. Option tables come from the coreutils 8.32 `--help` output, with coreutils 9 additions where they change stream use, such as `cksum --check`. Common GNU/Linux options and file operands affect stream-usage hints. Advanced scripts, unseen script files, unknown options, and dynamic arguments retain conservative hints where needed. It does not inspect files or check permissions. Other commands and unsupported argument forms remain conservative; filenames opened by commands themselves (for example, `tee`) are not mapped. Usage assumes standard commands without aliases or replacement functions. “No writes” is an inference, never a measured byte count. Diagnostics remain possible, including when stderr is merged into a pipe. Descriptors above 2 are drawn on their cards and listed in Descriptor details; routes and boxes are for 0–2. Pipelines can be joined into a list with `&&`, `||`, `;`, or new lines; they are drawn one above another, since each runs after the one before. Background jobs (`&`), control structures, command substitutions, here-documents, and dynamic redirect filenames produce an error. Process substitutions must be separate words (`2> >(cmd)`, not `2>(cmd)`), and Bash's descriptor numbering is assumed to start at 63. It does not model aliases, functions, shell options, or inherited descriptors beyond 0–2.

Semantics follow the Bash manual sections on [redirections](https://www.gnu.org/s/bash/manual/html_node/Redirections.html) and [pipelines](https://www.gnu.org/software/bash/manual/html_node/Pipelines).

Command usage references: [GNU Coreutils](https://www.gnu.org/software/coreutils/manual/html_node/index.html), [GNU time](https://www.gnu.org/software/time/manual/html_node/Invoking-time.html), [GNU xargs](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), [GNU find](https://www.gnu.org/software/findutils/manual/html_node/find_html/index.html), [GNU grep](https://www.gnu.org/software/grep/manual/grep.html), [curl](https://curl.se/docs/manpage.html), [GNU Wget](https://www.gnu.org/software/wget/manual/wget.html), [GNU awk](https://www.gnu.org/software/gawk/manual/html_node/Invoking-Summary.html), [GNU sed](https://www.gnu.org/software/sed/manual/sed.html), [util-linux rev](https://github.com/util-linux/util-linux/blob/master/text-utils/rev.1.adoc), and [pv](https://www.ivarch.com/programs/pv.shtml).
